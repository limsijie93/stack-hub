# Databricks CI/CD

> **Assumed layout** (adapt paths if your repo differs): Terraform modules under `terraform/modules/`, env foundation roots at `terraform/environments/<env>/`, and one folder per project at `projects/<project>/` with `env-tf/<env>/*.tfvars` + `src/`. Workflow and job names below (`<non_prod_apply_workflow>`, `<prod_apply_workflow>`, `<docs_check_workflow>`, and job labels like `<plan_job>` / `<apps_plan_job>` for the jobs/apps Terraform plan+apply jobs and `<apps_deploy_job>`) are placeholders — substitute your workflow names.

Use this skill to ship or change Databricks Jobs, Lakeflow Declarative Pipelines, Databricks Apps, and Unity Catalog MCP Services in your repo. Jobs/pipelines are config-driven via `cicd-jobs.tfvars`; apps via `apps.tfvars`; MCP services via `mcp.tfvars` — each its own Terraform root and state, one file per project per environment. **Do not edit Terraform module code for routine project work.**

## When to use

- Creating a new job (schedule / trigger / continuous) for a project.
- Adding, removing, or reordering tasks inside an existing job.
- Adding an LDP pipeline (`src/pipelines/<key>/`) or promoting one to `explicit-ldp` for custom libraries / clusters.
- Wiring notebooks, SQL, dbt, Spark Python, `run_job`, `for_each`, or `condition` tasks.
- Adding a Databricks App (`src/apps/<key>/`, authored in `apps.tfvars` — a separate file/root/state from `cicd-jobs.tfvars`) — a custom web service (FastAPI, Streamlit, Dash, …) for cases Model Serving can't cover: custom HTTP status codes, GET endpoints, or large payloads. See [`references/APPS.md`](references/APPS.md).
- Adding a Unity Catalog MCP service (authored in `mcp.tfvars` — a separate file/root/state) — registers a governed MCP endpoint backed by a UC HTTP connection, optionally created inline by the module. See the module README in your repo (e.g. `terraform/modules/databricks_mcp/README.md`).
- Adjusting permissions, notification emails, schedules, or `enabled` flags.
- Onboarding a project's `src/notebooks/`, `src/pipelines/<key>/`, `src/apps/<key>/`, `src/files/`, `src/requirements.txt`, `src/config/`, or `src/utils/` into auto-upload.
- Uploading files auto-discovery doesn't cover (any folder other than `config/`/`utils/`, or needing a custom destination `path`) via `workspace_files`.

## Rules

1. **Never change Terraform module code** to add a project job/pipeline — only edit the project's `cicd-jobs.tfvars` and files under `src/`.
2. **Keys are `^[A-Za-z0-9_]+$`** for `jobs`, `tasks`, `pipelines` — no hyphens. Resource names generate as `{key}-{project_name}`.
3. **LDP is the default pipeline type.** One folder `src/pipelines/<key>/` = one pipeline; serverless + Photon + channel `CURRENT` are forced. Never set `libraries`, `clusters`, `storage`, `target`, `run_as`, `event_log`, `filters`, `deployment`, `gateway_definition`, `name`, `channel`, `photon`, `serverless`, `edition`, `root_path`, `development`, `budget_policy_id`, `configuration`, `notifications`, or `tables` on an LDP pipeline — all are auto-managed by convention and rejected at plan time if set.
4. **Reserved Spark-conf keys** cannot be placed in `pipeline_configuration`: `env`, `project`, `target_catalog`, `landing_target_schema`, `refined_target_schema`, `feature_target_schema`, `legacy_base_path`, `pipeline_base_name`, `<metadata_framework>.project.root`. Override catalog/schema via the top-level `catalog` / `schema` fields instead.
5. **`explicit-ldp`** is the only escape hatch — `"explicit"` alone is invalid. Requires ≥1 library with extension `.py|.ipynb|.sql|.dbc`; `catalog`+`storage` and `schema`+`target` are mutually exclusive; serverless pipelines need `catalog` or `storage` and cannot define `clusters`.
6. **Every enabled job must set `email_notifications.on_failure`** (≥1 recipient). **Every LDP pipeline must set `notification_email_recipients`**. `description` is mandatory on jobs and pipelines.
7. **Each task picks exactly one task-type block** (`notebook_task`, `pipeline_task`, `spark_python_task`, `sql_task`, `dbt_task`, `condition_task`, `run_job_task`, `for_each_task`, `spark_jar_task`, `spark_submit_task`, `python_wheel_task`) and at most one of `schedule` / `trigger` / `continuous` on the job.
8. **Notebook tasks auto-resolve** to `src/notebooks/<task_key>` when `notebook_path` is unset — name the file to match the task key, or override via `task_to_notebook_mapping`.
9. **Reference pipelines by `pipeline_key`** (the map key), never by name or id.
10. **Prefer `enabled = false` over deletion** when temporarily disabling a job, task, or pipeline — it keeps state history intact.
11. **`requirements_file`** must be a relative path with no `..`. Job-level dependency injection uses `inject_requirements = true` and relies on `src/requirements.txt`. Code tasks (`notebook_task`, `spark_python_task`, `dbt_task`, `python_wheel_task`) auto-receive `environment_key = "Default"` — but only when they run on serverless (no `job_cluster_key` or `existing_cluster_id`). Combining `inject_requirements = true` with cluster compute on code tasks is rejected at plan time.
12. **Run access is `job_permissions`/`pipeline_permissions` — a bool for the project group, an email list for named individuals, never a group.** The project group always gets an access-control entry on every **enabled** job/pipeline; `project_group_can_run` (`true`/`false`) controls whether that's `CAN_MANAGE_RUN`/`CAN_RUN` or `CAN_VIEW`, defaulting to `true` in dev/uat and `false` in prod unless set explicitly. `run_access_emails` grants named individuals `CAN_MANAGE_RUN`/`CAN_RUN` directly — there is no `group_name` option on these two variables **by design**, and Terraform validation rejects a `group_name` grant of `CAN_MANAGE_RUN`/`CAN_RUN` even through the separate one-off `permissions` map. Giving `project_group_can_run = true` in prod, or adding anyone to `run_access_emails`, is a permission *exception*, not a routine config choice. An example policy you may adopt: (a) add an inline comment at the grant stating the reason and a removal-by date, and (b) open an exception ticket in your tracker with a matching removal date (for example, ≤ 3 months out) — see `references/SCHEMA.md`'s Permissions schema. These overrides only make sense in **prod**: dev/uat already default to full run access, so setting either field there is a no-op. Worked example: `projects/<example_project>/env-tf/prod/cicd-jobs.tfvars` (Permissions Configuration section).
13. **Databricks Apps (`apps.tfvars`, separate root/state) — Terraform creates the app, it never deploys code.** Not a block inside `cicd-jobs.tfvars`: apps deploy from `terraform/databricks-apps/` → `modules/databricks_apps`, from a project's own `apps.tfvars`, into `projects/<project>/apps/terraform.tfstate` — a project may have `apps.tfvars` with no `cicd-jobs.tfvars` at all. One folder `src/apps/<key>/` = one app, `app.yaml` required at its root. A separate `<apps_deploy_job>` GitHub Actions job runs `databricks apps deploy` after the apps root's apply completes — no provider version has a code-deployment argument on `databricks_app`. Only `description` is required; everything else defaults. **`schema_access`** (`"deployed"` default, `"project"`, or `"none"`) picks which schema the app's own service principal is granted against — `"deployed"` (dev/uat-only CI/CD-deployed catalog) or `"project"` (inception-owned project catalog, works in every env including prod); this is the prod-viable escape hatch. Apps have exactly two permission levels (`CAN_USE`/`CAN_MANAGE`, no `CAN_VIEW` floor), so access is the project group, the app's own dedicated access group, or named individuals — never `contributor_groups`. No native rollback — redeploy previous source (`git revert` + merge in prod). Apps bill continuously with no scale-to-zero. `references/APPS.md` covers the full schema, the prod `schema_access` caveat, and credential handoff.
14. **Unity Catalog MCP services (`mcp.tfvars`, separate root/state).** Deployed from `terraform/databricks-mcp/` → `modules/databricks_mcp`, from a project's own `mcp.tfvars`, into `projects/<project>/mcp/terraform.tfstate`. Registers `databricks_ai_gateway_mcp_service` resources in `<deployed_catalog>_<env>.<project_name>`. Each service requires a UC HTTP connection — either created inline (`connection = { host = "..." }`, experimental — blocked on enabled entries at plan time until provider support matures) or referenced pre-existing (`source_connection_name = "connections/..."`). Disabled entries (`enabled = false`) may omit both. **Keys are `^[A-Za-z0-9_]+$`** (same as jobs/pipelines). `description` is required; `comment` falls back to `description` when unset. Rate limits support `RATE_LIMIT_KEY_SERVICE`, `RATE_LIMIT_KEY_SERVICE_PRINCIPAL`, `RATE_LIMIT_KEY_USER`, `RATE_LIMIT_KEY_USER_DEFAULT`, `RATE_LIMIT_KEY_USER_GROUP`; principal-dependent keys (`USER`, `USER_GROUP`, `SERVICE_PRINCIPAL`) require a non-empty `principal`, while `SERVICE` and `USER_DEFAULT` must not set one. **Grants** are supported via the `grants` field (`databricks_grant` with an `mcp_service` target) — manage them through Terraform rather than applying manually to avoid unmanaged drift. **Caveat:** MCP support in the provider is experimental, including inline connection mode. The deployed schema (`<deployed_catalog>_<env>.<project_name>`) must exist before the MCP root can register services — ensure a `cicd-jobs.tfvars` has been applied for the project, or use a project that already has one. Pin your provider version; MCP resources need ≥ 1.135.0.

## Workflow

1. **Open the project's tfvars** — `cicd-jobs.tfvars` for jobs/pipelines, `apps.tfvars` for apps, `mcp.tfvars` for MCP services, all at `projects/<project>/env-tf/<env>/`, edited independently. If none exists, copy from the corresponding `projects/<example_project>/env-tf/dev/` example.
2. **Plan the change** — for a job/pipeline, against [`references/SCHEMA.md`](references/SCHEMA.md), identifying which schema block (jobs / tasks / pipelines) you're touching; for an app, against [`references/APPS.md`](references/APPS.md)'s full schema; for MCP, against Rule 14 above and the MCP module README in your repo (e.g. `terraform/modules/databricks_mcp/README.md`).
3. **Make the edit** — in `cicd-jobs.tfvars` for a job/pipeline (keys snake_case, add `description` + notifications, wire `depends_on` via task keys), in `apps.tfvars` for an app (only `description` is required; everything else defaults — see APPS.md), or in `mcp.tfvars` for an MCP service (`description` and either `connection` or `source_connection_name` required).
4. **Drop source files** under `src/` if needed:
   - Notebook task `ingest` → `src/notebooks/ingest.py` (or `.ipynb`).
   - LDP pipeline `my_feature_store` → folder `src/pipelines/my_feature_store/` containing `.py`/`.sql`/`.ipynb` sources (and optional `requirements.txt`).
   - App `my_app` → folder `src/apps/my_app/` containing `app.py`, `app.yaml` (required), and `requirements.txt`. See [`references/APPS.md`](references/APPS.md).
   - UC volume files → `src/files/…`.
5. **Update project documentation** — mandatory before raising a PR (enforced by `<docs_check_workflow>`).
   Load [`assets/README_template.md`](assets/README_template.md) and [`assets/RELEASELOG_template.md`](assets/RELEASELOG_template.md) when creating these files for the first time.
   - `projects/<project>/README.md` — add/update the Project Structure tree to reflect any new `env-tf/`, `src/notebooks/`, `src/pipelines/` entries added in this change.
   - `projects/<project>/RELEASELOG.md` — append a row to the Summary table and add a detailed release section:
     - **Type**: `CI/CD Deployment` for jobs/pipelines; `Project Inception` for first `project.tfvars`; `Feature` for a new capability/extension.
     - **What shipped**: list every job, pipeline, notebook, and file created or changed.
     - **Deployment status** — for a **single-unit project**, include a per-release `Environments` table and mark only the env(s) applied in this PR. For a **multi-pipeline project** (>1 independently-deployed job or LDP pipeline — not LDP pipelines only, e.g. a project mixing LDP pipelines with a scheduled job), instead maintain a top-level **Deployment Status** section — a project-level inception table plus one deployment table per job or pipeline (see the multi-pipeline variant in [`assets/RELEASELOG_template.md`](assets/RELEASELOG_template.md)) — and update the row(s) for the job(s)/pipeline(s) this PR touched.
   - Canonical examples: `projects/<example_project>/{README.md,RELEASELOG.md}` (single-unit), `projects/<multi_pipeline_project>/{README.md,RELEASELOG.md}` (multi-pipeline).

   **Doc checklist** (verify before committing):
   - [ ] `README.md` Project Structure tree matches the actual folder contents
   - [ ] `RELEASELOG.md` Summary table has a new row with today's date and correct type
   - [ ] `RELEASELOG.md` release section lists all resources shipped
   - [ ] Deployment status updated — per-release `Environments` table (single-unit) or the top-level **Deployment Status** table(s) for the touched job/pipeline (multi-pipeline)
   - [ ] Both files end with exactly one newline (no trailing blank line)
6. **Run pre-commit locally**: `pre-commit run --all-files` (validates fmt + terraform_validate where applicable).
7. **Deploy to dev/uat** via `workflow_dispatch` on `<non_prod_apply_workflow>` — it runs `<plan_job>` (jobs) and/or `<apps_plan_job>` (apps) depending on which tfvars file the project has; verify the job/pipeline runs green in the Databricks workspace. If the project has apps, `<apps_plan_job>` is followed by the `<apps_deploy_job>` job — verify each app reaches `RUNNING` state, and hit its URL directly at least once.
8. **For prod**, raise a PR to `main` — `<prod_apply_workflow>` runs `plan` on the PR and `apply` only after merge (branch-protected per your org's policy), with the same jobs/apps split as non-prod; `<apps_deploy_job>` runs on the merge, not the PR.

## Watch for

- **Hidden coupling to `src/` files** — renaming a task without renaming the notebook will break auto-resolution of `notebook_path`.
- **Reserved Spark-conf keys** silently fail plan validation — use the `catalog`/`schema` fields, not `pipeline_configuration`.
- **LDP forbidden fields** — if you need a cluster, libraries list, or custom storage, flip to `type = "explicit-ldp"` deliberately; don't try to sneak them into an `ldp` pipeline.
- **Permission levels are API-restricted** — Jobs: `CAN_VIEW`, `CAN_MANAGE_RUN` only (`IS_OWNER` is not grantable via API). Pipelines: `CAN_VIEW`, `CAN_RUN`. Notebooks/workspace files: `CAN_READ`, `CAN_RUN`, `CAN_EDIT`, `CAN_MANAGE`. Directories: `CAN_READ`, `CAN_EDIT`, `CAN_MANAGE` (no `CAN_RUN`). Clusters: `CAN_ATTACH_TO`, `CAN_RESTART`, `CAN_MANAGE`. Instance pools: `CAN_ATTACH_TO`, `CAN_MANAGE`. This ceiling is fixed in every environment — it's a Databricks API constraint, not a policy choice.
- **`project_group_can_run` default is env-conditional, not fixed** — dev/uat default to `true`; prod defaults to `false`. It's a single root-wide setting per `cicd-jobs.tfvars` (`job_permissions.project_group_can_run` / `pipeline_permissions.project_group_can_run`), not per-job/per-pipeline — there's no way to give one job in the map a different project-group level than the rest without going through the separate `permissions` map instead. Elevating above the env default is a permission exception — see Rule 12.
- **Prod drift** — never edit Databricks resources directly in the UI; the next `apply` will overwrite changes.
- **Pipeline key vs folder name** — `directory` defaults to `pipeline_key`; if the folder under `src/pipelines/` is named differently, set `directory` explicitly.
- **Requirements path traversal** — `requirements_file = "requirements.txt"` is correct; `"../shared/requirements.txt"` is rejected.
- **`environmentMetadata` in `.ipynb` files** — the Databricks UI embeds a workspace-specific `environmentMetadata` key when saving notebooks; this breaks cross-workspace promotion because the target workspace cannot resolve the source environment ID. Your infra pipeline workflow should strip it with your CI's notebook-env strip step immediately after checkout in both plan and apply jobs — no author action required. Troubleshoot: if promotion still fails due to this key, verify that strip step ran.
- **CI/CD-deployed catalog is automatic (dev/uat only)** — every project with a `cicd-jobs.tfvars` gets a schema + `EXTERNAL` volume in the shared `<deployed_catalog>_<env>` catalog (SP-writable, group read-only), separate from the interactive `projects_<env>.<project>` schema. No `cicd-jobs.tfvars` field is required for this; see `references/SCHEMA.md`'s "CI/CD-deployed catalog" section if a project needs to opt out. **This is also why an App's `schema_access = "deployed"` (the default) and `enable_telemetry` fail in prod** — the apps root's plan precondition rejects `"deployed"` outright there (no separate CI/CD-deployed catalog exists in prod); use `schema_access = "project"` instead, which resolves to the inception-owned project catalog in every environment. See `references/APPS.md`.
- **An app's `schema_access = "deployed"` depends on the jobs root having applied first** — the deployed schema is created by the *jobs* root (`databricks-jobs`), not the apps root, so the apps root resolves it via a `data "databricks_schema"` lookup rather than a Terraform dependency (a `depends_on` can't cross state files). The calling workflow sequences `<apps_plan_job>` after `<plan_job>` (`needs:`) so this lookup succeeds on a project's very first dispatch; a missing schema fails plan with the provider's own "not found" error.
- **An App's `app.yaml` is a single static file shared across every environment** — it cannot contain per-environment literal values. Anything that varies by environment (a catalog name, a warehouse ID) must come from a `resources` binding + `valueFrom`, resolved by Terraform per environment, never hardcoded in `app.yaml` or duplicated by re-deriving `<deployed_catalog>_<env>` logic in `cicd-jobs.tfvars`.
- **Every `databricks apps deploy` is a new deployment, not an in-place code update in the deploy job's absence** — if you edit `src/apps/<key>/` and the `<apps_deploy_job>` job did not run (workflow skipped, failed, or was never re-triggered), the app keeps serving its previous code indefinitely. A green Terraform apply does not by itself mean the app's code changed.
- **Shared packages — import, don't vendor** — if your org ships shared Python packages for `src/` code (e.g. shared packages preinstalled in the base environment), import them. Pull add-on wheels in via the pipeline `requirements_file` / `python_dependencies` or job-level `inject_requirements`; never copy their code into `src/`.
